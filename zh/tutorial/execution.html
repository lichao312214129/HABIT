并行执行与容错#

HabitatSpec 声明 算什么 。 RunPolicy （及执行后端）声明 如何 调度受试者。若 random_seed 固定，串行 ↔ 进程池切换不会改变科学数值。

本页为集成章。逐旋钮参考： 执行后端 。可运行演示： 执行后端上的原子组件 。

初学者可在队列变慢或单受试者导致运行崩溃前忽略本页。快速开始已用小进程池（ workers=2 ）。

选择后端#

backend_from_policy() 选择：

  • policy.backend == "process" 或 workers > 1 或 parallel_mode == "isolated" 时用 ProcessPoolBackend

  • 否则 SerialBackend

仅设置正的 subject_timeout_sec 并不会 强制 spawn（默认为 900.0 ）。超时隔离仍需 backend="process" 或 parallel_mode="isolated" 。

用途

策略

调试单受试者 / notebook

RunPolicy(workers=1, backend="serial")

队列，默认隔离

RunPolicy(workers=2, backend="process", subject_timeout_sec=900.0)

每受试者新进程

同上，另加 parallel_mode="isolated" （更高 spawn 成本）

重要

Windows + 进程池： 生成 worker 会重新导入你的脚本。任何会启动 ProcessPoolBackend 的调用（ RunPolicy(backend="process") 、 workers > 1 或 parallel_mode="isolated" ）必须放在以下代码块内:

if __name__ == "__main__":
    ...

Running the same code at module top level (or pasting it into a .py file without this guard) raises RuntimeError: ... bootstrapping phase on Windows. The habit CLI entry point is already safe; this applies to scripts / notebooks converted to scripts / pure-Python recipes. For a quick serial check, use RunPolicy(workers=1, backend="serial") (no spawn).

将 backend 传入 recipe 或 map():

from habit.contracts import cohort_from_directory
from habit.datasets import fetch_demo
from habit.execution import backend_from_policy
from habit.recipes import one_step_habitat
from habit.spec import RunPolicy

# Change DATA / MODALITIES / ROI to your preprocessed layout
DATA = fetch_demo()  # or "demo_data/preprocessed"
MODALITIES = ("LAP",)
ROI = "LAP"
cohort = cohort_from_directory(DATA, modalities=MODALITIES, roi=ROI)[:2]
study = one_step_habitat(
    modalities=MODALITIES, n_habitats=3, random_seed=0, roi=ROI
)
policy = RunPolicy(
    workers=1,
    backend="serial",
    subject_timeout_sec=None,
    on_subject_failure="continue",
    resume=True,
)
backend = backend_from_policy(policy)
result = study.fit_predict(cohort, backend=backend)

原子路径（无 Study ）：本进程 extract 纹理、预处理、拟合，再 backend.map assigner 于已在内存的单元。该纹理的受试者 vs 队列预处理及等价 HabitatSpec 见 纹理特征图：单独与联合强度 。同一 study 串行 vs 池化及时序见首 gallery 页。

失败策略#

两后端均接受 on_subject_failure ：

  • "continue" （默认）— 在该受试者槽记录异常并继续

  • "fail_fast" —— 首个受试者异常即抛出

map() 在任槽位失败时仍抛出 ProcessingError ， 即使 后端用了 continue 。Recipes / CLI 传 raise_on_failure=False 以便部分队列完成。直接 backend.map 则异常留在 slot.error 。

两者，在一项有一名未完成受试者的研究上： 执行后端上的原子组件 。

Per-受试者 wall-clock cap: subject_timeout_sec (ProcessPool only). Expiry raises SubjectTimeoutError.

运行中对不稳定受试者的重试： auto_retry_rounds （ProcessPool）。发生致命 MemoryError 后， oom_backoff=True 会减少 workers 。

恢复与检查点#

附加 CheckpointStore 使第二次运行跳过已记录成功的受试者： 执行后端上的原子组件 。

已记录 failures 除非 retry_failed_subjects=True 否则跳过。用 force_rerun_subjects 强制若干 ID。

生境配方/CLI 路径上，缓存键嵌入 spec 指纹。在不换新存储的情况下更改提取器或预处理阶段会像对 错误 定义的缓存命中——应视为新运行。

其他软失败旋钮#

非执行后端，但同样是“抛出 vs 继续”的思路：

  • GeometryPolicy —— 图像与掩膜网格（ STRICT / RESAMPLE_MASK / …）

  • extract_batch(fail_fast=) — 对成对样本做特征提取

  • load_plugins(strict=) — 缺失的第三方插件

  • HabitatModel.load — 拒绝非 habit.habitatmodel 文件（ CompatibilityError ）

YAML 配置#

原生 v1 文档使用顶层 policy: 块（ workers 、 backend 、 subject_timeout_sec 等）。旧 YAML 在文档顶层保留相同旋钮（ processes 、 individual_subject_timeout_sec 等）。字段重命名表： Spec、RunPolicy 和 YAML 同构 。完整生境参考： 生境分割配置 。
