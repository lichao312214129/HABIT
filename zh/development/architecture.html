Architecture#

自 v1.0.0 起 HABIT 为 API-first ：Python API 即产品，CLI 与 YAML 配置为其薄壳。代码库组织为六层，L0 底至 L5 顶。层只能向下 import，使数值核心无 I/O、配置解析不进算法。

按以下顺序阅读公开的开发者文档：

  1. 本页 — 分层、公开 API 边界、不变量。

  2. Contributing — environment, tests, and pull requests.

  3. 扩展 HABIT — 注册表和入口点插件。

设计原则#

  1. API first ：每项研究为 Study （ result = recipes.Study(spec=spec).fit_predict(cohort) 且 HabitatSpec.stages ）；YAML 与 CLI 为同一调用的投影。生境工厂（ two_step_habitat / one_step_habitat / direct_pooling_habitat ）返回带声明设计的 Study。

  2. Typed specifications ：分析声明为不可变、带指纹的 spec 对象（HabitatSpec 、MLSpec ），而非松散字典。

  3. 注册表模式 ：算法按名称注册，而非硬编码进工作流逻辑。

  4. Unified contracts ：数据以类型化契约在层间传递（Subject 、FeatureTable 、HabitatModel 等）。

  5. 惰性导入 ：可选且体积大的依赖仅在需要时加载。

六层架构#

  subgraph L5["L5 — interfaces (habit/cli.py, habit/commands/)"]
    CLI["CLI commands"]
    YAML["YAML documents"]
  end
  L4["L4 — recipes (habit/recipes/)<br/>Study.fit / fit_predict / predict<br/>two_step_habitat · one_step_habitat · direct_pooling_habitat<br/>train_model · cross_validate · predict_model<br/>extract · radiomics · compare_models · run_from_yaml"]
  L3["L3 — domain (habit/domain/)<br/>protocols + component registries<br/>SubjectPipeline · TablePipeline"]
  L2["L2 — contracts (habit/contracts/)<br/>Subject · Cohort · FeatureTable<br/>HabitatModel · RunManifest"]

  L5 --> L4
  L4 --> L3
  L3 --> L2
  L2 --> L1
  L1 --> L0

栈旁支持包： habit/spec/ （spec 对象与 v0.1→v1 转换器）、 habit/execution/ （并行后端与检查点）、 habit/datasets/ （合成数据）、 habit/plugins/ （组件发现）、 habit/schemas/ （v0.1 YAML schema）、 habit/compat/ （v0.1 引擎，保留 YAML parity 与旧文件）。

Public Python symbols are listed under API 参考. A third party should be able to call op(subject) or Study(spec).fit_predict(cohort) without HABIT's directory layout. If habit/cli.py and habit/commands/ were deleted, the scientific capability would still be callable.

两条执行路径#

The v1 path (specs and recipes). Python callers build a spec, assemble a 队列 or 特征 table through the contracts/adapters, and call a recipe. The recipe wires domain components from the L3 registries into a pipeline, runs it through an execution backend, and returns a typed result with a RunManifest for provenance:

        flowchart TD
  S["HabitatSpec / MLSpec<br/>(immutable, fingerprinted)"] --> R["habit.recipes.*"]
  C["Cohort / FeatureTable"] --> R
  R --> P["SubjectPipeline / TablePipeline<br/>(L3 registries resolve Spec('name', params))"]
  P --> X["Execution backend<br/>serial / multiprocessing"]
  X --> RES["StudyResult / ModelResult<br/>+ RunManifest"]

v0.1 路径（YAML schema 与配置器）。 CLI 仍接受 v0.1 YAML。命令对照 habit/schemas/ 中 Pydantic schema 校验，用 LegacyConfigAdapter 转换，再调用 相同 v1 配方。经典 schema → 配置器 → 编排器链仅存于 habit/compat/engines/ ，少数工作流（特征提取、传统放射组学、旧 pickle 预测）仍经此路由：

        flowchart TD
  Y["v0.1 YAML"] --> SC["habit/schemas/<br/>Pydantic validation"]
  SC --> TR["LegacyConfigAdapter<br/>translate to v1"]
  TR --> REC["habit.recipes.*<br/>(same as the Python path)"]
  SC -.->|"extract / radiomics /<br/>legacy pickles"| CF["compat configurators<br/>MLConfigurator etc."]
  CF --> ORC["compat orchestrators<br/>BatchProcessor · HabitatAnalysis<br/>KFoldWorkflow"]

Maintainer notes for the YAML loader, PathResolver, and compat engine tours live in the repository at developer/sphinx_archive/ (configuration_system.rst, request_lifecycle.rst, subsystems.rst).

关键组件#

  • Specs （ habit/spec/ ）将分析声明为数据。spec 不可变、可序列化、可指纹化，保存的模型始终知道产生它的分析。

  • Recipes （ habit/recipes/ ）是标准研究设计。是多数用户与全部 entry point 唯一需要的编排。

  • 契约 (habit/contracts/) are the typed data model; every layer speaks in these objects.

  • Domain registries （ habit/domain/ ）将 Spec("kmeans", {...}) 组件引用映射到实现。

  • Execution backends （ habit/execution/ ）运行受试者并行工作并为中断队列提供检查点。

  • Compat engines （ habit/compat/engines/ ）是 v1 前实现（ BatchProcessor 、 HabitatAnalysis 、 HoldoutWorkflow/KFoldWorkflow ）。YAML parity 工作流仍完全支持，但不再是架构重心。

Subsystems#

Habitat analysis 支持三种策略 — two_step 、 one_step 、 direct_pooling — 作为同一领域组件上的 v1 配方实现。拟合状态以自描述 .habitatmodel 归档持久化以供可复现预测。

预处理 and tabular machine learning are supporting shells: habit preprocess calls habit.recipes.preprocess_images(); train_model() / cross_validate() / predict_model() run a TablePipeline. Compat engines under habit/compat/engines/ remain for YAML parity. Those trees are frozen for product work; 生境分析 is the extension surface.

CLI 到核心映射#

每条 CLI 命令为 L5 装配：解析验证 YAML、必要时转换、调用 recipe、写输出。命令层无算法。

设计哲学#

成像论文需要 可重复 且 可复现 的生境图。体素强度依赖扫描仪与预处理；聚类依赖 \(k\) 与特征向量；单个体素掩膜偏移可改写放射组学图。HABIT 不能消除该物理。它使改变生境图的选择 显式、有类型并随结果携带 （HabitatModel 、Spec 、describe_methods() ）。单元测试通过不等于多中心复现。

产品答案是可复制进 notebook 或另一流水线的 库 API 。CLI 与 YAML 是该 API 的壳，非第二套科学栈。默认（k-means 生境数：inertia elbow ，\(kin[2,10]\) ）是起始协议，非声称默认对每个肿瘤最优。

由此产生五个工程支柱：

  1. Configuration is an interface ，非一层 — YAML 与 Python 经 Spec 共享语义。

  2. Schemas fail fast — Pydantic 在计算前验证；严格处 extra='forbid' 。

  3. Registry 解耦算法 ——按名切换实现。

  4. Train and predict share a contract — inference reuses fitted state, including 队列级 preprocessing on HabitatModel.

  5. Commands stay thin — L5 委托 habit.recipes 。

Invariants#

These rules must not be broken. Most are checked by tests/test_architecture_contracts.py.

重要

提交变更前运行架构契约测试:

pytest tests/test_architecture_contracts.py -m unit

科学正确性

Invariant

Rationale

防止数据泄露

特征 selection, scaling, and resampling must be inside one sklearn Pipeline and fitted only on training folds.

Train/predict symmetry

predict 须复用 fit 学到的聚类中心、缩放参数、所选特征等状态。

Controlled randomness

每一个随机步骤都必须接受并传递一个随机种子，以便可以重现相同的配置。

Configuration

  • 根配置模型在需严格验证处用 extra='forbid' 。新字段须在 schema 中声明。

  • habit/schemas/ 是 schema 定义的真相源。兼容模块可再导出 schema 但不得定义重复。

  • 可配置 params 的组件须定义并注册 Pydantic 参数模型（v0.1 YAML）或在组件构造函数上暴露（v1 Registry.create ）。

  • v1 spec objects (habit/spec/) are immutable and fingerprinted; a fitted model must always be traceable to the exact spec that produced it.

Registry contracts

所有注册表必须：

  • 继承相应 _BaseRegistry 子类；

  • 暴露 register 、 get 、 available 、 register_params_model 、 get_params_model ；

  • 保留独立 _registry 字典；

  • 从 available() 返回一个列表。

类工厂另提供 create() 。可调用注册表提供其可调用入口访问器。

Orchestrator contracts

每个顶层编排器须暴露 ORCHESTRATOR_CONTRACT 声明的终端方法。批处理器与工作流通常暴露 run() ；生境分析暴露 fit() 与 predict() 。

工程惯例

  • Use habit/utils/progress_utils.py for all progress bars.

  • 可复用跨子系统工具放在 habit/utils/ 。

  • 图内生成的文字必须为英文。

  • 在命令或工厂方法内部懒加载导入重量级可选依赖。

  • Keep business logic out of the command layer: commands are L5 wiring that delegate to habit/recipes/; v0.1 engine logic lives in compat/engines/*/run.py.

  • 遵守层方向：L0 kernel 保持纯函数（无 I/O、状态、日志），且不得向上 import。

  • 显式标注函数输入输出，代码注释用英文。
